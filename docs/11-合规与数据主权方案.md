# TeleOps 合规与数据主权方案（等保 · 数据出域 · 模型私有化）

> 版本基线：v0.8.49 ｜ 定位：**纯方案层**，不要求立刻改代码；目的是给「百人内部电信团队」上线前
> 把合规红线想清楚、把改造代价标出来。衔接：`docs/10-生产部署清单（百人规模）.md`（部署形态）、
> `docs/04`（能力对照）、`docs/06`（多副本）。
>
> ⚠️ 免责声明：本文是工程视角的合规梳理与改造可行性评估，**不构成法律意见**。等保定级、数据出境
> 路径须由具备资质的机构/法务按现行法规最终认定。

## 1. 为什么这是红线，不是可选项

TeleOps 处理的是**电信内部运维告警、设备拓扑、日志片段、指标时序**——这些在电信行业语境下
可能落入「重要数据」「关键信息基础设施（关基）运营者数据」范畴。一旦把内容送到**公有云第三方 LLM**
（当前默认 `https://api.deepseek.com/v1`）推理，就触发三条法律的并集约束：

| 法规 | 相关义务 | 对本项目的影响 |
|---|---|---|
| 《网络安全法》 | 关基运营者境内存储、出境安全评估 | 拓扑/告警若属关基数据，出境需评估 |
| 《数据安全法》 | 数据分类分级、重要数据出境管理 | 需先给数据定级，再决定能否出境 |
| 《个人信息保护法》(PIPL) | 个人信息出境需单独同意/评估 | 告警若含人员/账号等 PII 同样受限 |

**结论先行**：面向百人内部电信团队、处理真实运维数据上生产前，**默认「数据不出域 + 模型私有化」
是合规最低门槛**，而不是可选项。下面给出可落地的改造方案与代价。

---

## 2. 等保级别建议（判断框架，非定论）

等保 2.0 按受侵害客体与程度定级。运维平台一般归「第三级」评估起步（一旦承载关基或大量重要数据），
**最少不低于第二级**。判断要素：

| 要素 | 本项目情形 | 指向级别 |
|---|---|---|
| 受侵害客体 | 公民/法人权益 + 社会秩序 +（可能）公共利益 | 多客体叠加 |
| 数据敏感度 | 拓扑/告警/日志可能含重要数据 | 抬级 |
| 系统角色 | 运维支撑系统（非直接生产系统） | 但影响面大 |
| 使用规模 | 百人内部，但若误发告警/误处置有业务影响 | 中 |

**建议**：以**三级**做差距分析（三级要求最全，达标后向下兼容二级），由测评机构定级备案。
三级核心控制项与本项目已有能力的映射见第 5 节——**多数已天然满足，缺口主要是「不出域」与「信创」**。

## 3. 数据主权与数据出域专项

### 3.1 默认架构的数据流风险
```
  内部告警/拓扑/日志 ──► TeleOps 后端 ──► DeepSeek 公有云 API ──► 推理结果
       （境内机房）        （境内）           （数据出境 ⚠）
```
即使后端在境内，**推理请求体里的 host、指标、日志片段、拓扑节点名会离开企业边界**。

### 3.2 缓解措施（按代价从低到高）
1. **模型私有化（首选，零/最小代码改动）**：见第 4 节，把 `TELEOPS_LLM_BASE_URL` 指向本地推理服务，
   数据根本不出去。
2. **数据脱敏中间件（新增钩子）**：在 LLM 调用前对告警体做 PII/资产名遮蔽（host 泛化、账号打码、
   拓扑节点别名化），保留诊断所需语义、去掉可识别信息。
3. **最小化采集**：只送根因所需字段，不送全文日志/全量拓扑。
4. **不出域推理 + 审计留痕**：所有送第三方的内容在审计里记「出域动作」，便于事后举证与合规审计。
5. **数据分类分级前置**：先和法务/数据安全岗把「哪些字段算重要数据」定清楚，再决定能否出境。

## 4. 模型私有化方案（已具备配置化能力）

本项目 LLM 调用**完全配置驱动**，替换底座是**改环境变量、零代码改动**：

| 变量 | 默认值 | 私有化改法 |
|---|---|---|
| `TELEOPS_LLM_BASE_URL` | `https://api.deepseek.com/v1` | 改成本地 OpenAI 兼容端点，如 `http://gpu-node:8000/v1` |
| `TELEOPS_LLM_MODEL` | `deepseek-chat` | 改成本地模型名，如 `qwen2.5-32b-instruct` |
| `TELEOPS_LLM_API_KEY` | DeepSeek Key | 本地服务可不设或设占位 |
| `TELEOPS_LLM_PROVIDER` | `deepseek` | 保持兼容客户端即可（OpenAI 协议通吃） |

**落地路径**：
- **轻量**：用 **vLLM / Ollama** 在内部 GPU 节点起一个 OpenAI 兼容服务，指向它即可。
- **信创**：鲲鹏/海光 + 昇腾 NPU 推理（MindIE / 国产推理框架），同样走 OpenAI 兼容协议。
- **模型选型**：RCA 任务对中文 + 推理链要求高，可选 Qwen2.5-32B/72B、DeepSeek-R1 蒸馏版、GLM-4 等本地权重。
- **降级保障**：未配 Key 时后端自动走**离线 Mock**，演示与断网环境零依赖可跑（已验证）。

> 注意：私有化后**推理质量与延迟**由本地算力决定，需在真实样本上做根因 Top-1 / 噪声抑制率回归
> （`src/eval/rootcause_bench.py`），确保私有模型不显著掉指标。

## 5. 等保 2.0 技术要求映射（本项目已有能力）

| 控制类 | 三级要求 | TeleOps 现状 | 差距 |
|---|---|---|---|
| 身份鉴别 | 唯一标识、口令/双因子 | JWT 多用户 + 邀请码 + OIDC SSO + 写 Token | 双因子待加（OTP/SSO 已可补） |
| 访问控制 | 最小权限、角色分离 | 多租户三层隔离 + **RBAC 角色运营（v0.8.49）** | 已满足最小权限 |
| 安全审计 | 审计留存 ≥6 个月、可 replay | 可回放审计时间线 + CSV 导出 + **OSS 归档（v0.8.48）** + 越权留痕 | 留存周期按 OSS 归档可满足 |
| 入侵防范 | 边界防护、异常监测 | 零依赖限流（XFF 正确分桶）+ 防火墙白名单 + 邀请码 | 已满足基础项 |
| 数据完整性/保密性 | 传输加密、存储保护 | Caddy 全链路 HTTPS + 审计旁路不落明文口令 | 存储加密（磁盘/库）建议补 |
| 集中管控 | 统一运维审计 | Grafana/Prometheus 可观测 + `/metrics` | 已具备 |

**关键结论**：等保的「身份/访问/审计/入侵」四类硬要求本项目**基本已对齐甚至超过求职作品平均水平**，
真正缺的是 **① 数据不出域（第 3/4 节）** 与 **② 信创全栈（第 6 节）**，且两者都是**方案级、低代码改动**。

## 6. 信创适配（可选，按单位要求）

| 层 | 国产化替换 | 本项目兼容点 |
|---|---|---|
| CPU | 鲲鹏/海光/飞腾 | Python 服务跨架构，重新构建镜像即可 |
| OS | 麒麟/统信 UOS | 同 Linux 生态，Docker 直接跑 |
| 数据库 | 达梦/人大金仓/OceanBase | 已有 Postgres 方言层（`TELEOPS_DB_DSN`），换 DSN + 补方言即可 |
| 推理 | 昇腾/寒武纪 NPU | OpenAI 兼容协议，改 `BASE_URL` |
| 中间件 | 东方通/宝兰德 | 非强依赖，可替换 |

## 7. 合规落地路线图（纯方案，分阶段）

- **阶段 0（立即，零代码）**：`TELEOPS_LLM_BASE_URL` 指向本地推理；数据不出域最小闭环跑通。
- **阶段 1（测评准备）**：补双因子（OTP/SSO 已具备）、存储加密、审计留存周期确认（OSS 归档已支撑）、
  写《访问控制策略》《应急预案》等文档（方法论验收清单 RACI/ADR/风险登记册可在此复用）。
- **阶段 2（信创，按单位要求）**：OS/CPU/DB/推理全栈国产化替换，做等保三级测评。

## 8. 结论与衔接

- **部署形态（docs/10）与合规边界（本文）正交**：先按本文定「数据能否出境、模型是否私有化」的边界，
  再回 docs/10 选形态 A/B。若选数据不出域，形态 B 的 Redis/Postgres 也**必须同机房/同域内部署**，
  不得用公有云托管实例。
- **改造代价总评**：默认架构→合规版，**核心是一行 `BASE_URL` 改动 + 脱敏钩子 + 信创替换**，
  不涉及重构；RBAC/审计/HTTPS/限流等合规硬项早已就位。
- **上线前一句话红线**：百人内部电信生产，**未做数据不出域与模型私有化前，不得接入真实告警/拓扑/日志**。
