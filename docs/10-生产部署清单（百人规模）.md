# TeleOps 生产部署清单（百人规模 · 内部电信团队）

> 版本基线：v0.8.49 ｜ 用途：给「百人以上电信内部团队」自托管运维告警 RCA 作战室的可落地部署 runbook。
> 衔接：`deploy/README.md`（Phase 0 单节点入门）是本文前提；`docs/06`（多副本/Redis 实战）是形态 B 的底层依据；
> `docs/11-合规与数据主权方案.md`（待办①）是上线前的数据出境/模型私有化检查前置。

---

## 0. 这份文档解决什么

`deploy/README.md` 的 Phase 0 方案是**单 backend + Caddy + SQLite**，**没有组织级多进程/多副本、也没有外部状态**。
它适合面试演示与个人作品集，**直接扛百人内部日常使用会先撞三道墙**：

| 墙 | 现象 | 解法 |
|---|---|---|
| SQLite 单写 | 百人并发写审计/业务 → 锁等待堆积、偶发 `database is locked` | 切 **Postgres**（多副本写入前置） |
| 单进程单副本 | 一个 backend 进程扛全部诊断/造工具 job → CPU 打满、无容错 | **多 worker 多进程** 或 **多副本** |
| 内存态状态 | 限流/任务/流/信号量在进程内 → 多副本各持一份、互相看不见 | `TELEOPS_STATE_STORE=redis` 外置 |

本文给出**两套经过代码验证的部署形态**，并附容量评估、一键命令、头号坑、备份回滚、上线检查清单。

> 已实现底座（直接复用，无需改代码）：多租户三层隔离、JWT 多用户 + 写接口 Token、邀请码、零依赖限流（**已正确读 `X-Forwarded-For`**）、Caddy 自动 HTTPS、Postgres 方言层（`TELEOPS_DB_DSN`）、多 worker/多副本（`teleops_ctl.py --workers/--port` + `TELEOPS_BACKENDS`）、Redis 状态外部化（`TELEOPS_STATE_STORE=redis`）、可回放审计、OSS 归档、RBAC 角色运营（v0.8.49）。

## 1. 容量评估（百人内部团队）

| 维度 | 推荐值 | 说明 |
|---|---|---|
| 并发在线 | 100 人，峰值同时操作 ~20–30 人 | 告警流大屏是**轮询 + 增量拉取**，不是长连接，压力远低于 IM |
| CPU | 形态 A：8 核；形态 B：2×4 核 | 瓶颈在 LLM 调用等待（IO 密集）+ 偶发造工具 job（CPU 尖峰） |
| 内存 | 形态 A：16 GB；形态 B：2×8 GB | uvicorn 多进程每 worker ~300–500 MB；Chromadb 开着另加 ~1 GB |
| 磁盘 | 系统 40 GB + 数据卷 50 GB（含知识库/生成工具/审计归档） | 审计按 100 人 × 日均 ~500 操作估算，年增长 ~数 GB；Postgres 另计 |
| 带宽 | 上行 ≥ 20 Mbps | 主要是告警 JSON / 指标 / 日志回传与前端静态资源 |
| 副本 | 形态 A：1 控制面 + N worker；形态 B：2+ 无状态副本 | 见形态定义 |
| 数据库 | 形态 A 可 SQLite；**形态 B 必须 Postgres** | 多进程/多副本写并发只有 Postgres 扛得住 |

**经验阈值**：百人内、操作不密集 → 形态 A 足矣；要求**故障切换不影响在跑告警流** → 形态 B。
无论哪种，对外一律走 **Caddy HTTPS 反代**，绝不直接把 8000 暴露公网。

## 2. 两种部署形态

### 形态 A：单机容器化（推荐起步，性价比最高）
```
                 ┌──────────────── 一台 8C16G 服务器 ────────────────┐
  浏览器/内网 ──► │  Caddy :443 (HTTPS, 自动证书)                    │
                 │      │ reverse_proxy backend:8000                 │
                 │      ▼                                           │
                 │  backend 容器（uvicorn --workers 4，进程内状态）   │
                 │      │                                           │
                 │  Postgres 容器（profile pg，业务数据落库）         │
                 │  [可选] Prometheus+Grafana（profile observability）│
                 └──────────────────────────────────────────────────┘
```
- 适用：百人内、单点故障可接受（重启 30s 内恢复）。
- 状态：默认进程内（单容器多进程，共享同一进程内存，无跨容器问题）。
- **不需要 Redis**（单容器内部状态一致）。

### 形态 B：高可用多副本（故障切换零感知）
```
               Caddy :443 (HTTPS)
                  │ reverse_proxy {upstreams}   ← TELEOPS_BACKENDS 多 upstream
        ┌─────────┼─────────┐
     backend:8000 backend:8001 backend:8002   （无状态副本，各自 uvicorn）
        │           │           │
        └─────┬─────┴─────┬─────┘
           Postgres     Redis (TELEOPS_STATE_STORE=redis)
        （共享业务库）  （限流/任务/流/信号量外置，副本间一致）
```
- 适用：要求某副本宕机时**在跑的告警流不中断**、限流额度不被重置、任务不丢。
- **必做**：`TELEOPS_STATE_STORE=redis`（v0.8.34 已验证，7/7 通过）；**必须 Postgres**。
- Redis ≥ 4.0（RQ 多字段 HSET），生产建议 6+；旧版/代理用 `TELEOPS_REDIS_PROTOCOL=2` 降级 RESP2。
- 副本身份：`TELEOPS_REPLICA_ID` 注入 `/health`/`/metrics`，健康检查打 `/health` 看 `replica_id`。

> 形态 B 在 Docker 里用 `docker compose up -d --scale backend=N --profile pg`：compose 内嵌 DNS 会把
> `backend:8000` 轮询到 N 个副本；配套用 `scripts/Caddyfile`（`{upstreams}` 模板）替换 `deploy/Caddyfile`，
> 由 `caddy_runner` 按 `TELEOPS_BACKENDS` 渲染多 upstream。

## 3. 一键部署步骤（基于现有 `deploy/docker-compose.yml`）

### 3.1 准备密钥（沿用 Phase 0）
```bash
cd /path/to/TeleOps
cp deploy/.env.example deploy/.env
nano deploy/.env           # 至少填 DEEPSEEK_API_KEY、TELEOPS_DOMAIN、TELEOPS_ACME_EMAIL
```
百人生产**必加**：
```
TELEOPS_INVITE_CODE=<内部邀请码>        # 关闭开放注册，防陌生人注册
TELEOPS_API_TOKEN=<强随机串>            # 开启写接口 Token 鉴权（前端「设置」填相同值）
TELEOPS_DB_DSN=postgresql://teleops:teleops@postgres:5432/teleops   # 切 Postgres
```

### 3.2 形态 A：单机 + Postgres + 多 worker
```bash
# 启动 backend + caddy + postgres（--profile pg 拉起 Postgres）
docker compose -f deploy/docker-compose.yml --profile pg up -d --build

# 把 backend 提到多进程：临时覆盖 command（或改 compose 的 backend.command）
docker compose -f deploy/docker-compose.yml run -d --service-ports \
  -e TELEOPS_DB_DSN=postgresql://teleops:teleops@postgres:5432/teleops \
  backend uvicorn src.api.server:app --host 0.0.0.0 --port 8000 --workers 4
```
> 更干净的做法：在 `deploy/docker-compose.yml` 的 `backend` 下加
> `command: ["sh","-c","uvicorn src.api.server:app --host 0.0.0.0 --port 8000 --workers 4"]`
> 并保留 `depends_on: [postgres]`（取消 compose 中那三行注释）。

### 3.3 形态 B：多副本 + Redis（追加 Redis 服务）
在 `deploy/docker-compose.yml` 的 `services:` 下追加（与 `postgres` 同级）：
```yaml
  redis:
    image: redis:7-alpine
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
    volumes:
      - teleops_redis:/data
volumes:
  teleops_redis:
```
并在 `backend.environment` 追加 `TELEOPS_STATE_STORE: "redis"` 与
`TELEOPS_REDIS_URL: ${TELEOPS_REDIS_URL:-redis://redis:6379/0}`，`depends_on` 加 `redis`。
然后：
```bash
# 多副本：2 个 backend 容器，Caddy 轮询；用 scripts/Caddyfile 渲染多 upstream
docker compose -f deploy/docker-compose.yml --profile pg up -d --scale backend=2 --build
```

### 3.4 验证
```bash
curl -I https://你的域名/health        # 期望 200，且响应体含 replica_id / 限流状态
curl -s https://你的域名/health | python -m json.tool
docker compose -f deploy/docker-compose.yml ps     # backend/caddy/postgres 全 healthy
```

## 4. 头号坑专项（百人反代场景，已防但别改坏）

**限流按错 IP → 全员 127.0.0.1 → 2–3 人即 429。**
本项目限流**已正确读 `X-Forwarded-For`**（`src/core/rate_limit.py` + `server._rl_key`：
登录用户按 JWT `sub` 分桶，未登录按 XFF 真实客户端 IP；反代链用 `trusted_proxies` 防伪造）。
**保持两条铁律**：
1. Caddy 侧 `trusted_proxies static private_ranges` 已配（deploy/Caddyfile），**不要删**——否则 XFF 不被信任。
2. 若前面再叠一层 Nginx/SLB，也要把那层加进 `trusted_proxies`，并确认它透传 `X-Forwarded-For`。
3. 健康检查打 `/health` **不算额度**（/health /metrics /static 已豁免），别把探针算成限流。

**端口监听才是健康真相**：进程 PID 存活 ≠ 服务健康，一切以 `netstat`/`/health` 监听为准（与进程管理铁律一致）。

**HTTPS 必套反代**：JWT/密码/Token 明文 HTTP 有截获风险；百人内网也必须 HTTPS（Caddy 自动证书）。

## 5. 备份与回滚

| 对象 | 命令 |
|---|---|
| Postgres（形态 A/B） | `docker exec <pg> pg_dump -U teleops teleops \| gzip > backup/teleops-$(date +%F).sql.gz` |
| 业务卷（SQLite 兜底/工具/知识库） | `docker run --rm -v teleops_data:/data -v $PWD/backup:/backup alpine cp -r /data /backup` |
| 回滚版本 | `git checkout <旧tag>` 后 `docker compose up -d --build`；DB 不向下兼容时先恢复对应备份 |
| 审计归档 | `POST /audit/archive` 已落 OSS/本地 mock，独立于业务库，可单独保留 |

**最低限度**：Postgres 每日 dump + `teleops_data/kb/tools` 卷每周备份。回滚前先停副本、恢复库、再起。

## 6. 健康检查与监控

- `/health`（liveness：进程+DB 存活、运行中任务数、限流状态）、`/metrics`（Prometheus 文本，零依赖）。
- 可观测性：`--profile observability` 一键拉起 Prometheus + Grafana（预置「TeleOps 运行概览」面板：
  QPS/状态码/延迟分位/**429 限流**/任务·LLM 速率/业务 gauge/运行时长）。
- **生产务必**：Grafana 移除匿名访问两行 + 改强密码（见 `deploy/.env` `GRAFANA_ADMIN_*`）。
- 告警流业务指标：根因 Top-1 命中率、噪声抑制率、MTTR（MTTR 待真实工单数据，见待办②）。

## 7. 安全上线前检查清单（百人内部也照做）

- [ ] 域名 A 记录指向公网 IP；安全组/防火墙放行 **80+443**（80 用于 ACME 验证）。
- [ ] `TELEOPS_ACME_EMAIL` 真实邮箱；Caddy 自动申请/续期 Let's Encrypt 证书。
- [ ] `TELEOPS_API_TOKEN` 已设，前端「设置」填相同值（写接口鉴权）。
- [ ] `TELEOPS_INVITE_CODE` 已设（关闭开放注册）。
- [ ] 数据库：百人/多副本 → **Postgres**（勿用 SQLite 扛并发写）。
- [ ] 多副本 → `TELEOPS_STATE_STORE=redis` + Redis ≥ 4.0（建议 6+）。
- [ ] Caddy `trusted_proxies` 保留，XFF 限流不被破坏。
- [ ] Grafana 强密码 + 关匿名；Prometheus 不对外暴露。
- [ ] 备份：Postgres 每日 dump + 业务卷周备，回滚演练过一次。
- [ ] **数据主权/模型私有化**：默认 DeepSeek 走公有云，告警内容会**出境**——百人内部合规务必先过
      `docs/11-合规与数据主权方案.md`（等保级别、数据出域评估、私有化 LLM 替换）。

## 8. 运维命令速查

```bash
# 启/停/重启/状态（含 --port 多副本）
python scripts/teleops_ctl.py start --workers 4          # 裸启多进程（也可容器化）
python scripts/teleops_ctl.py status
docker compose -f deploy/docker-compose.yml --profile pg up -d
docker compose -f deploy/docker-compose.yml ps
docker compose -f deploy/docker-compose.yml logs -f backend
docker compose -f deploy/docker-compose.yml down         # 停（保留卷）
docker compose -f deploy/docker-compose.yml down -v      # 停（删卷，⚠ 清空数据）
# Caddy 多副本渲染
python scripts/caddy_runner.py        # 按 TELEOPS_BACKENDS 渲染 scripts/Caddyfile → 启动
```
