# 06 · 多副本部署实战验证与运维指南

> 对应演进：D3（状态外部化）收官 + Phase 2→3 桥梁。本文记录「TeleOps 跑多副本、
> 共享状态、任意副本可见/可控同一条告警流」的实战验证结论与部署运维要点。
>
> 验证版本：`v0.8.34`（2026-09-25 实战验证通过，7/7 断言 + 4 类状态集成测试全绿）。

---

## 1. 一句话结论

TeleOps 的 D3 改造把四类共享状态（限流 / 任务 / 流状态 / 并发闸门）全部抽到 Redis 后端。
只要设置 `TELEOPS_STATE_STORE=redis`，**N 个 API 副本就是无状态的**——任一副本发起的
任务、流、限流计数、信号量，其它副本立即可见、可接管。

但「流」有两层，务必分清（这是本次验证最重要的一条认知）：

| 平面 | 作用 | 多副本共享？ | 依赖 |
|------|------|--------------|------|
| **状态/控制面** | 流的 running/rounds、谁启动的、谁停 | ✅ 天然跨副本（RedisStreamStateStore） | `TELEOPS_STATE_STORE=redis` + 任意 Redis |
| **播放面** | 逐条告警的真实处置播放 | ✅ 设计上跨副本（RQ worker 消费队列） | `TELEOPS_STREAM_EXECUTOR=queue` + Redis ≥4.0 + Unix `fork()` worker |

- **默认** `TELEOPS_STREAM_EXECUTOR=thread`：播放在进程内线程，**不跨副本**（"与现状一致"，供单机/演示零依赖）。
- 要验证/启用「多副本流共享」，**必须切 `queue`**：状态落 Redis，任何副本都能看/停这条流。
- Windows 无 `os.fork()`，RQ worker 起不来 → Windows 只能验证**状态/控制面**共享（已通过），
  真正的逐条播放由 Linux/WSL2 部署态的 worker 消费。

## 2. 环境变量速查

| 变量 | 取值 | 说明 |
|------|------|------|
| `TELEOPS_STATE_STORE` | `local`（默认）/ `redis` | 四类共享状态的存储后端总开关 |
| `TELEOPS_REDIS_URL` | `redis://host:port/0` | Redis 连接串（所有状态共用） |
| `TELEOPS_REDIS_PROTOCOL` | 不设置=redis-py 默认(RESP3) / `2`=RESP2 | **旧版或代理 Redis 不支持 HELLO 时设 `2`** |
| `TELEOPS_STREAM_EXECUTOR` | `thread`（默认）/ `queue` | 流执行器；多副本共享流状态需 `queue` |
| `TELEOPS_REPLICA_ID` | `hostname:pid`（默认，可显式注入） | 副本可观测标识，注入 `/health` `/api/info` `/metrics` |
| `TELEOPS_API_TOKEN` | 字符串 | 等价于 admin（写操作需 admin/域 owner） |
| `TELEOPS_STATE_STORE_FAIL_OPEN` | `on`（默认）/ `off` | Redis 故障时是否放行（旁路故障不压垮业务） |

> `TELEOPS_REDIS_PROTOCOL` 只影响握手协议，由 `src/core/redis_factory.py` 统一处理，
> 应用代码无需感知。生产用 Redis 6+ 时**不要设**（走 RESP3，性能好、特性全）。

## 3. 部署拓扑（推荐）

```
                 ┌───────────────── 负载均衡 / 反代（按 IP 或 JWT 粘性均可，
                 │                  因为状态在 Redis，无粘性也能正确工作）
                 │
   ┌─────────────┴─────────────┐
   │  replica-A  :8001          │   │  replica-B  :8002          │   ... 可横向扩
   │  (uvicorn, 无状态)         │   │  (uvicorn, 无状态)         │
   └─────────────┬─────────────┘   └─────────────┬─────────────┘
                 │ 全部共享同一份 Redis            │
                 └──────────────┬─────────────────┘
                          ┌──────┴──────┐
                          │   Redis    │  ← 状态/控制面（必选，≥4.0 建议 6+）
                          │  (独立实例) │
                          └──────┬──────┘
                                 │ 播放队列（RQ）
                          ┌──────┴──────┐
                          │  RQ worker  │  ← 播放面（仅 queue 模式需要，需 Unix fork）
                          │  (Linux)    │
                          └─────────────┘
```

启动任一副本（环境变量相同，仅端口/replica_id 不同）：

```bash
TELEOPS_STATE_STORE=redis \
TELEOPS_REDIS_URL=redis://127.0.0.1:6379/0 \
TELEOPS_STREAM_EXECUTOR=queue \          # 多副本共享流状态（可选；不设为线程模式=单机）
TELEOPS_REPLICA_ID=replica-A \
TELEOPS_API_TOKEN=<your-admin-token> \
python -m uvicorn src.api.server:app --host 0.0.0.0 --port 8001
```

> 反代/健康检查：打任意副本的 `/health`，返回体含 `replica_id`；
> `/metrics` 暴露 `teleops_replica_info{replica_id="..."}` gauge，便于Prometheus 分副本观测。
> 对外开放前务必套 HTTPS 反代（密码/JWT 明文 HTTP 有截获风险）。

## 4. 实战验证（已通过）

### 4.1 实时双副本验证（HTTP 层面，证明"任意副本可见/可控"）

```bash
python scripts/multi_replica_validate.py
```

脚本自动：起真实 Redis（纯内存）+ 两个 uvicorn 副本（8001/8002，均 `STATE_STORE=redis`
+ `STREAM_EXECUTOR=queue`），断言：

1. 两副本 `/health` 暴露不同 `replica_id`；
2. 副本 A 在 `core-net` 启动流 → 副本 B `/stream/status` 立即可见 `running=True`；
3. 副本 B 能跨进程停止该流，副本 A 随后也确认已停止。

**结果：7/7 通过**（2026-09-25，v0.8.34）。

### 4.2 永久回归守卫（四类状态跨进程共享）

```bash
python -m pytest tests/test_multi_replica_redis.py -q
```

用真实 Redis 二进制起纯内存实例，为每类状态建两个独立实例（模拟两个副本），
断言「A 写入/占用，B 立即可见」：

- `test_ratelimit_shared_across_replicas` — 限流配额跨副本共享
- `test_jobstore_shared_across_replicas` — 异步任务状态跨副本共享
- `test_streamstate_shared_across_replicas` — 流状态跨副本共享（D3 核心）
- `test_semaphore_shared_across_replicas` — 并发闸门许可池跨副本共享

**结果：4/4 通过。** 前置：`tools/redis/redis-server.exe` 存在（从 nuget `redis-64`
解压，已加入 `.gitignore`，不入仓库）；缺失则整文件 `skip`，CI 不红。

## 5. 两个必须知道的 Redis 兼容性坑（本次验证实测）

### 5.1 HELLO / RESP3 握手（连接层）

- **现象**：用 redis-64 3.0.503（Windows 可用的最老移植版）时，redis-py 8.x 默认
  RESP3 握手发 `HELLO` 命令 → `unknown command 'HELLO'`，连接失败、API 500。
- **原因**：`HELLO` 是 Redis 6.0 才引入的。
- **解法**：设 `TELEOPS_REDIS_PROTOCOL=2` 降级到 RESP2（不发 HELLO）。生产用
  Redis 6+ 时不设，走 RESP3。统一经 `src/core/redis_factory.py` 工厂，业务代码零改动。

### 5.2 RQ 多字段 HSET（播放面）

- **现象**：`TELEOPS_STREAM_EXECUTOR=queue` 下 `/stream/start` 入队 RQ 任务时报
  `wrong number of arguments for 'hset' command`。
- **原因**：RQ 2.x 入队用**多字段 HSET**，Redis 4.0 才支持；redis-64 3.0.503 只支持
  单字段 HSET。
- **解法**：
  - 生产/部署态用 Redis **≥4.0**（建议 6+），RQ 入队即正常，无需任何代码改动；
  - 已在 `QueueStreamExecutor.start` 做**入队容错**：状态面（D3 多副本核心承诺）已落
    Redis 即视为成功，入队失败仅告警不阻断启动。Windows 开发机可用此路径验证状态共享，
    播放由 Linux worker 恢复。

> **推论**：D3 的「状态/控制面」对任何 Redis 都生效；只有「播放面」要求 Redis ≥4.0。
> 这是部署 Redis 版本的硬性前置条件，选 Redis 时务必 ≥4.0（优先 6+ 以同时吃 RESP3）。

## 6. 运维 checklist

- [ ] Redis 独立部署、有密码/ACL，版本 **≥4.0（建议 6+）**；
- [ ] 所有副本 `TELEOPS_STATE_STORE=redis` 且 `TELEOPS_REDIS_URL` 指向同一实例；
- [ ] 旧版/代理 Redis 设 `TELEOPS_REDIS_PROTOCOL=2`；
- [ ] 多副本共享流：副本 `TELEOPS_STREAM_EXECUTOR=queue`，且 Linux 侧起 RQ worker；
- [ ] 显式注入 `TELEOPS_REPLICA_ID`（容器/编排下用 pod 名，便于排障）；
- [ ] 反代对外 HTTPS；健康检查打 `/health` 看 `replica_id`；
- [ ] 监控 `/metrics` 的 `teleops_replica_info`，确认各副本都被调度到；
- [ ] 改 Redis 后端后务必重启副本（状态后端在进程内缓存单例，改环境变量不同步）；
- [ ] 发布前跑 `pytest tests/test_multi_replica_redis.py` 回归。

## 7. 已知限制

- **Windows 无 RQ worker**：只能验证状态/控制面；逐条播放需在 Unix 部署态消费队列。
- **默认值仍是单机友好**：`TELEOPS_STATE_STORE=local` + `TELEOPS_STREAM_EXECUTOR=thread`
  下，副本各自内存态，互为孤岛——这是有意为之的零依赖默认值，不是 bug。上多副本前
  务必显式切 `redis`（+ 按需 `queue`）。
- **状态后端是进程内缓存单例**：改 `TELEOPS_STATE_STORE` 等环境变量后必须重启进程，
  改 DB/配置文件不会热同步（与 registry 同理）。
