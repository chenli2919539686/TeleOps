# TeleOps 架构承压与缺陷分析

> 目的：不谈"卖给谁 / 用在什么场景"，只回答一个问题——**多少人用的时候会出事、架构在哪些点上会塌**。
> 所有结论均对照当前代码（`VERSION=0.8.24`）实证，标注 `文件:行号`。
> 部署形态：单机单进程，`python -m uvicorn src.api.server:app` 启动（无 `--workers`，`scripts/teleops_ctl.py:170` + `src/api/server.py:1939`），Caddy 443 反代到 127.0.0.1:8000，DB 为 SQLite（`data/teleops.db`）。

---

## 〇、结论先行（给你一个直观的容量画像）

| 问题 | 当前真相 |
|---|---|
| 设计容量定位 | **演示级 / 单人-小团队内部**（1–3 人安心用） |
| 最致命缺陷 | 套 Caddy 后**限流按 `request.client.host`=127.0.0.1**，全员共用一个桶 → **约 2–3 个活跃用户或 4–6 个浏览器标签页就全员 429** |
| 核心价值路径天花板 | 告警→根因被全局 `LLM_SEM=4` 卡死，LLM 并发上限 ≈ **80 次/分**（DeepSeek 延迟 2–5s 估算） |
| 能否水平扩容 | **不能**。registry / SSE 流 / 任务 / 限流计数 / 信号量全在进程内存，DB 是 SQLite 单写者；加副本只会更糟 |
| 安全与限流是否互斥 | **当前互斥**：走 Caddy(HTTPS) 限流就崩；直连 8000(无 HTTPS) 限流才正常 |

---

## 一、按用户规模推算：多少人用会出事

假设前端每标签页每 2–3 秒轮询一次（作战室实时刷新是典型做法），读接口 ≈ 20–30 次/分/标签。
限流桶为 `READ=120/min`、`WRITE=60/min`、`LOGIN=5/min`（`src/core/rate_limit.py:26-28`）。

| 规模 | 现象 | 根因 | 严重度 |
|---|---|---|---|
| **1 人 / 1–2 标签** | 正常 | — | ✅ |
| **2–3 人同时活跃（经 Caddy）** | 全员开始偶发 429，刷新转圈 | 限流 key 全是 `read:127.0.0.1`（`server.py:178`），共享一个 120/min 桶 | 🔴 致命 |
| **4–6 个浏览器标签（经 Caddy）** | 几乎必定 429，整个实例拒绝服务 | 同上；轮询即可打满共享桶 | 🔴 致命 |
| **同域多人同时处置告警** | 先到先得，超出 4 个 LLM 调用开始排队，延迟从秒级升到分钟级 | 全局 `LLM_SEM=4`（`server.py:377-378`，`server.py:1045`） | 🟠 高 |
| **≈80 个并发告警处置** | LLM 路径饱和，新告警平均等待 >30s | 4 并发 × (1/3s) ≈ 80/min 上限，受 DeepSeek 账号并发配额约束 | 🟠 高 |
| **多人同时写（建 Agent/域/审批）** | 偶发 `database is locked` / 写入超时 | SQLite 单写者（`workspace_store` 全量落 SQLite） | 🟡 中 |
| **数十人注册/登录（经 Caddy）** | 第 6 人起 `login:127.0.0.1` 5/min 超限 → 429，无法 onboarding | `login:` 桶同样被代理 IP 污染（`server.py:179-180`） | 🔴 致命（新人进不来） |

> **一句话**：在"推荐部署"（Caddy HTTPS， README 明确要求对外必须套 HTTPS）下，TeleOps 目前**撑不住 3 个真实用户**。这不是性能问题，是**限流取 IP 的逻辑 bug**——它和健康加固建议（用 Caddy）直接冲突。

## 二、架构缺陷清单（按严重度，带实证与修法）

### 🔴 P0-1 限流在反向代理后失效 / 反向误杀全员
- **位置**：`src/api/server.py:178`（`_RateLimitMiddleware` 用 `request.client.host`）；同类正确写法在 `server.py:203-208` 的 `_client_ip()`（读 `X-Forwarded-For`），但**限流没调用它**。
- **影响**：Caddy 反代后 `request.client.host` 恒为 `127.0.0.1`，所有用户共享一个限流桶 → 多用户即 429（见上表）。直连 8000 反而正常，导致"要 HTTPS 就废限流、要限流就裸 HTTP"的互斥。
- **修法**：中间件改 `client = _client_ip(request) or "unknown"`，并把 `_LOW_FREQ_PATHS`/静态放行逻辑保留。一行级改动，风险极低，收益最高。

### 🔴 P0-2 登录/注册限额同样被代理 IP 污染
- **位置**：`server.py:179-180`（`login:{client}`）。
- **影响**：经 Caddy 时 `login:127.0.0.1` 5/min，小团队集中登录/注册直接 429，新人进不来。
- **修法**：同 P0-1，统一用 `_client_ip()`。

### 🟠 P1-1 核心价值路径被全局 LLM 信号量(4) 卡死
- **位置**：`server.py:377-378`（`LLM_SEM=Semaphore(4)`）、`server.py:1045`（`with LLM_SEM, _agent_sem(aid)`）。
- **影响**：所有业务域、所有用户的 LLM 推理共享 4 个并发槽；DeepSeek 延迟 2–5s → 上限 ≈ 80 次/分。这是"多少人能同时用核心功能"的硬天花板。
- **修法**：① 调高 `TELEOPS_LLM_CONCURRENCY`（受账号配额约束）；② 对可批处理请求做合并/异步队列；③ 长告警流用后台任务 + SSE 推送，避免占住请求线程。

### 🟠 P1-2 SSE 流按业务域单槽建键
- **位置**：`server.py:372`（`_streams: Dict[str, AlertStream]`）、`server.py:394-400`（`_stream_of(ws_id)` 每域一个 `AlertStream`）。
- **影响**：同一业务域只有一条流水线实例。多用户/多标签订阅同一域时依赖 `AlertStream` 内部广播；若某端点"启动流"时未判断 `running` 可能重复拉起流水线。属于**需现场验证**项：建议确认 `AlertStream.run()` 有 `running` 守卫，否则同域二次进入会双跑。
- **修法**：流以"域"为单位做广播订阅即可（作战室本就该共享视图）；但启动入口必须幂等（`if not stream.running: stream.run(...)`）。

### 🟡 P2-1 进程内状态，零水平扩容能力（架构天花板）
- **位置**：`registry`（内存，`src/core/agent_registry.py`）、`_streams`/`_jobs`（`server.py:372,413`）、限流 `_hits`（`rate_limit.py:30`）、信号量（`server.py:378,389`）。
- **影响**：全部存单一进程内存。要扛"很多人"，本应加副本，但当前加副本会：各副本 registry 不一致、限流各算各的、SQLite 多进程写冲突。**架构上现在只能垂直Scale（单台加核/加内存），且 Python GIL 让多核红利有限**（单 worker，见下）。
- **修法（演进）**：限流→Redis；流/任务→Redis Pub/Sub 或共享队列；registry→DB 加载 + 共享缓存；信号量→Redis；DB→Postgres。详见第三节。

### 🟡 P2-2 单 uvicorn worker，GIL 限制 CPU 并行
- **位置**：`teleops_ctl.py:170`（`python -m uvicorn` 无 `--workers`）、`server.py:1939`（`uvicorn.run(app, ...)` 单进程）。
- **影响**：异步事件环可 hold 数百空闲连接（I/O 友好），但任何 CPU 尖峰（LangGraph 构图、大告警 JSON 解析、正则）会阻塞事件环 → 全站延迟抖动。多核机器只用到 1 核。
- **修法**：I/O 为主可暂不动；CPU 尖峰大时改 `uvicorn` 多 worker（需先解决 P2-1 的进程内状态外部化，否则多 worker 状态分裂）。

### 🟡 P2-3 SQLite 写并发瓶颈
- **位置**：审计日志（每次操作追加）、`set_agent_status`（`agent_registry.py:124`）、建/删 Agent·域·审批全量落 SQLite。
- **影响**：SQLite 单写者，并发写 → `database is locked`、写入超时。前端轮询 + SSE 频繁刷状态会放大写压力。
- **修法**：审计写改成批量/异步落盘；状态更新合并；高并发换 Postgres 或审计走独立写队列。

### 🟢 P3 Caddy upstream 写死单后端
- **位置**：`scripts/Caddyfile`（反代 `127.0.0.1:8000` 单目标）。
- **影响**：即使未来跑多 worker/多副本，Caddy 也只打到 8000，无法负载均衡。属"扩容前置依赖"。
- **修法**： upstream 改为多后端列表（配合 P2-1/P2-2）。

## 三、推荐演进路线（先治标 → 再治本）

### Phase 0（≈1 小时，立刻做，低风险高回报）
1. 限流中间件改用 `_client_ip(request)`（修 P0-1 / P0-2）——**解锁多用户**，是"能不能给人用"的开关。
2. 确认 `AlertStream.run()` 有 `running` 幂等守卫（修 P1-2 隐患）。

### Phase 1（容量调优，不改架构）
3. 按 DeepSeek 账号并发配额上调 `TELEOPS_LLM_CONCURRENCY`；长流程改后台任务+SSE（缓解 P1-1）。
4. 审计/状态写改为异步批量（缓解 P2-3）。

### Phase 2（去单点，为扩容铺路）
5. DB：SQLite → Postgres；registry 改为从 DB 加载 + 共享缓存（解 P2-1）。
6. 状态外部化：限流计数 / 流 / 任务 / 信号量 → Redis（解 P2-1、P0 在多副本下也需 Redis 才正确）。
7. `uvicorn` 多 worker + Caddy upstream 多后端（解 P2-2、P3）。

### Phase 3（真·多副本）
8. 无状态化后端实例，前面 Caddy/LB 负载均衡，全部共享 Redis + Postgres → 此时"多少人用"取决于 Redis/PG/DeepSeek 配额，而非架构缺陷。

## 四、你现在这版"安全并发用户数"建议

- **经 Caddy(HTTPS) 部署**：修 P0 前，**≤1 个真实用户**才稳（多人必 429）；修 P0 后，受 LLM_SEM(4) 约束，**约 10–20 个并发活跃用户**内体验良好，超过后根因处置排队变慢。
- **直连 8000(无 HTTPS) 部署**：限流正常，但违背安全规范（明文密码/JWT 有截获风险），仅适合本机自测。
- **硬上限**：单进程下 LLM 路径 ≈ 80 次/分；若要"几百人同时用核心功能"，必须走 Phase 2–3。

> 一句话总结：**当前最大坑不是性能，是"套了推荐的反代会限流全崩"这个逻辑 bug；修它只要改一行取 IP 的逻辑，就能从"1 人塌"变成"小团队可用"。真正撑大规模需要把进程内状态外部化（Redis/PG），那是 Phase 2 的架构债。**
