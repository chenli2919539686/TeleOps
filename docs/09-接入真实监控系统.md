# 09 · 接入真实监控系统（Grafana / Prometheus / Loki）

> 对应演进：MCP 接真实运维系统（v0.8.40 落地）。
> 目标：把 TeleOps 的监控接入从「demo 仿真」切换为「真连你现场的 Prometheus / Grafana / Loki」，
> 让运维 Agent 在诊断阶段能主动拉真实指标 / 日志。

---

## 1. 三个适配器各自负责什么

| 适配器 id | 系统 | 协议 / 端点 | 核心方法 | 用途 |
|---|---|---|---|---|
| `metrics-grafana` | Grafana 数据源代理 | `POST /api/v1/query_range`（经 Grafana 代理，可指向 Prometheus/InfluxDB…） | `query_metrics` | 指标时序（代理任意数据源） |
| `metrics-prometheus` | Prometheus 直连 | `GET /api/v1/query_range` | `query_metrics` | 指标时序（直连 Prometheus） |
| `logs-loki` | Loki | `GET /loki/api/v1/query_range` | `fetch_recent`（LogQL） | 日志切片（故障定位） |

> `log-elk`（Elasticsearch `_search`）此前已实现，复用同一套 `fetch_recent` 接口。
> Grafana 与 Prometheus 二选一即可（前者走代理、后者直连）；Loki 负责日志。

**默认行为（未配置）**：三者都返回**仿真时序 / 仿真日志**，保证演示、单测、离线环境零依赖。
只有当你在 `data/adapters.json` 填入真实 `base_url` 后，才会切到真实查询——这就是「配置驱动 + demo 兜底」。

---

## 2. 怎么切到真实监控（三步走）

### 2.1 准备 `data/adapters.json`

该文件已被 `.gitignore`，不入库（凭据不进版本库）。若还没有，从样例复制：

```bash
cp data/adapters.example.json data/adapters.json
```

在其中加入 / 修改对应段：

```json
{
  "metrics-prometheus": {
    "base_url": "http://prometheus.internal:9090",
    "api_key": "",                       // Prometheus 若开了 basic/auth 代理，填这里
    "verify_ssl": false
  },
  "logs-loki": {
    "base_url": "http://loki.internal:3100",
    "api_key": "",
    "verify_ssl": false
  }
}
```

> 端口默认：Prometheus `9090`、Loki `3100`、Grafana `3000`（Grafana 代理模式下 `base_url` 填 Grafana 地址）。
> `api_key` 用于 `Authorization: Bearer <key>`；若走反向代理的 basic auth，请改用网络层或代理侧处理。

### 2.2 重启后端

适配器配置在**进程启动时**一次性注入（与注册表、registry 同理，进程内缓存）。改 `data/adapters.json` 后必须**重启后端**：

```bash
python scripts/teleops_ctl.py restart
```

### 2.3 验证连通

- 后端启动后访问「适配器」页，看对应适配器的 `healthcheck`：
  - `mode=demo` 且 `reachable=True` → 仍在仿真（没配 base_url）；
  - `mode=live` 且 `reachable=True` → 已真连；`error` 字段会给出不通的原因（如 DNS / 401 / 自签证书）。
- 或用 API 直接探：

```bash
curl -X POST http://127.0.0.1:8000/adapters/metrics-prometheus/query \
  -H 'Content-Type: application/json' -d '{"promql":"up","hours":1}'
# -> {"mode":"live","promql":"up","series":[...]}   （真连）
# -> {"mode":"demo","promql":"up","series":[...]}   （未配置，仿真）
```

## 3. 把监控查询喂给运维 Agent（诊断增强 · v0.8.43 已落地）

Agent 当前诊断链路：`统一 Alert -> OpsAgent.rootcause(LLM) -> run_recommended_tools`。
让 Agent 在诊断时**主动查监控**的两种接法：

1. **手工喂（最快）**：在「作战室」对话里把 `query_metrics` / `fetch_recent` 的返回贴给 Agent 作为上下文——适合演示与排障。
2. **做成 Agent 诊断工具（已落地，v0.8.43）**：内核已内置两个只读诊断工具，注册进 `ToolRegistry` 并随基线工具播种：
   - `pull_metrics`（`tools/pull_metrics.py`）：调 `PrometheusAdapter` / `GrafanaAdapter.query_metrics`，参数 `query`(PromQL) + `hours`。
   - `pull_logs`（`tools/pull_logs.py`）：调 `LokiLogAdapter` / `ELKLogAdapter.fetch_recent`，参数 `query`(LogQL) + `limit`。

   二者均为**只读、低风险、无需人工确认**，与 `ping_host` / `restart_service` 同属基线工具（reset-demo / 清理脚本会保留）。
   `OpsAgent.rootcause` 的提示词已引导 LLM：当根因假设可由近期指标波动 / 日志关键字佐证时，在 `recommended_tool` 推荐这两个工具，并用 `tool_args`（JSON 对象）携带查询表达式（如 `{"query":"up","hours":1}` / `{"query":"{level=\"error\"}","limit":50}`）。
   `run_recommended_tools` 会把 `tool_args` 透传给工具执行器，并把告警主机作为 `host` 一并传入。

> 未配 `data/adapters.json` 时，这两个工具自动回退 demo 仿真（返回仿真时序 / 仿真日志），
> 因此**离线、单测、演示零依赖**；配了 `base_url` 即自动转真实查询（配置驱动 + demo 兜底）。
> 监控查询返回的是**实时观测值**，对「弱覆盖 / 干扰 / 传输丢包 / 拥塞」四类退化的根因判断是直接证据，
> 比纯文本描述强得多——这正是 TelcoNet 把 Grafana/Prometheus/Loki 列为标配的原因。

### 3.1 验证 Agent 真的调了监控工具

- 后端启动后访问「工具」页，基线工具里应能看到 `pull_metrics` / `pull_logs`（risk=low）。
- 跑一条真实告警触发闭环（`/stream/start` 或作战室派发），在返回的 `tool_results` 中观察：
  `recommended_tool=pull_metrics` 且 `result.mode` 为 `demo`（未配）/ `live`（已配）；
  日志类同理 `result.logs` 有内容。
- 单测：`tests/test_monitoring_tools.py`（执行器 demo/live 解析 + OpsAgent 集成调用 + tool_args 透传 + missing 检测，8 例全绿）。

## 4. 安全与网络注意

- `base_url` 指向内网监控组件即可，**不要**把 Prometheus/Loki 的端口直接暴露公网。
- 对外访问 TeleOps 必须套 HTTPS 反代（Caddy 已内置）；`api_key` 明文存 `data/adapters.json`，确保该文件不进版本库（已 gitignore）。
- 自签证书：把 `verify_ssl` 设为 `false` 可跳过校验（仅内网可信环境）；公网/跨信任域请设 `true` 并配好 CA。
